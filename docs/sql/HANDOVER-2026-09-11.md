# Prod SQL handover — 2026-09-11

Two migrations are written, verified and **not applied**. Both need the RDS master credentials,
which is why they are here rather than done: `quotes`, `quote_line_items` and everything the
catch-up touches are owned by `postgres`, not the service's `app_user`.

There is **no migration ledger in this project — merged is not applied**. Probe
`information_schema` before assuming any of this already ran; both files are idempotent, so a
re-run after a partial failure is safe and a re-run of something already applied is a no-op.

## The order rule, and why it is not negotiable

**Both files run BEFORE the image that reads their columns deploys.**

Prisma SELECTs every scalar column its generated client knows about. An image deployed against a
database missing these columns does not merely lose the new feature — it fails **every read of
`quotes`**: the estimate list, opening an estimate, and the webhook drain, all with
`column does not exist`. That is the Estimator down, not degraded.

Merging to `main` **is** the prod deploy here (CodeBuild → `techcopilot-prod-assistant`). So the
sequence is: run the SQL, verify, *then* merge.

## What to run

### 1. `docs/sql/prod-catchup-2026-09-10.sql` — everything pending since the 2026-09-07 apply

One CloudShell run, following `docs/CLOUDSHELL_PROD_SQL.md`. In dependency order it carries:
customers/sales-tax as entities, phase1b (tax snapshot, sub-customers, address, QBO sync columns),
phase3 (`customers` unique key → `NULLS NOT DISTINCT`), phase4 (proposal template library plus the
per-company `Default` data migration), phase7 (`zt_connections`), phase8 (ZenTrades write-back),
and the ownership/grants for the new tables.

It ends in a `DO` block that raises if anything it promised is missing, so a partial apply fails
loudly instead of reading as success. Success prints `PROD_CATCHUP_2026_09_10_APPLIED`.

**Deliberately excluded:** the CONTRACT phase (`docs/sql/phase2.sql`, which drops
`quotes.qbo_customer_id` / `qbo_customer_name` and the superseded `raw_*` tables). That runs only
*after* the new image is deployed and exercised — running it now breaks the **currently deployed**
image's quote reads. See the runbook's point-of-no-return note.

### 2. `bash docs/sql/apply-phase9.sh` — the estimate SyncToken baseline

Adds two nullable columns to `quotes`: `qbo_sync_token` and `qbo_remote_changed_at`. This is what
lets a webhook tell an estimate edited inside QuickBooks from the echo of our own post — without
it, re-completion silently overwrites the client's edit.

Unlike the catch-up, this one has its own apply script because it follows the phase-6 pattern: it
registers a throwaway task definition carrying the master credentials, runs the migration inside
the VPC on a one-off Fargate task, prints the output, and deregisters that revision on exit,
including on failure. Nothing about the running service is touched.

Success prints `PHASE9_APPLIED` (the label is derived from the filename by `build-runner.py`, so a
run cannot announce the wrong migration). No backfill: reading the current SyncToken for every
posted estimate would be one Intuit call per quote to establish a baseline that the next webhook
or re-completion establishes for free.

Order relative to step 1 does not matter — it touches only `quotes`, additively. Both must precede
the deploy.

## Then, and only then

Merge `feat/qbo-estimate-drift`. Verify afterwards **as `app_user`**, not as the migration role —
that distinction has bitten this project before (phase 1, 2026-09-08).

Two quick prod probes worth running once the image is up:

```sql
-- the vocabulary Intuit actually uses for this entity, which is why non-delete events were
-- being recorded rather than discarded
select operation, count(*) from qbo_webhook_events where entity = 'estimate' group by 1;

-- drift actually being detected
select count(*) from quotes where qbo_remote_changed_at is not null;
```
